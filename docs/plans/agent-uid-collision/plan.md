# Stop the traffic-agent's mesh bypass from matching application traffic (#4156)

## Problem

`agentinit` distinguishes the traffic-agent's traffic from the application's
with `-m owner --uid-owner <agentUID>` iptables matches. The mesh-bypass rule
(`--uid-owner <agentUID> ... -j RETURN`/`TEL_MESH_BYPASS`) exempts everything
matching that UID from service-mesh processing. The agent's UID, however, is
not distinct from the application's — in three ways:

1. **Inherited SC** (the systematic case): when no `agent.securityContext` is
   configured, the agent deliberately copies the securityContext of the first
   intercepted app container (`AgentSecurityContext()` in
   `pkg/agentconfig/container.go`). An app with `runAsUser: 1000` gives the
   agent uid 1000 — guaranteed collision.
2. **Root fallback**: with no securityContext anywhere, `AGENT_UID` is unset
   and `trafficAgentUID()` falls back to the init container's own uid — root.
   Any root-running app container collides.
3. **Operator choice**: `agent.securityContext.runAsUser` set equal to an app
   uid.

Consequence in a meshed pod: all app traffic matching the shared UID bypasses
the sidecar — no mTLS origination, no telemetry/policy, and (pre-#4157
behavior) broken mesh DNS. In a PERMISSIVE-mTLS mesh this degrades silently.

The SC inheritance is intentional and must stay: the agent mounts the app's
volumes and needs the app's permissions to serve them, and on OpenShift the
agent must run within the namespace's SCC UID range. A "force a unique UID"
fix is therefore off the table.

## Approach: distinguish by primary GID instead of UID

Give the agent container an explicit, distinct **primary group**
(`runAsGroup`), keep the inherited UID, and change the agent-discriminating
iptables matches from `--uid-owner` to `--gid-owner`.

Why this works:

- File access for volume serving is preserved: ownership bits work via the
  inherited UID; fsGroup-managed volumes grant access via *supplemental*
  groups, which `runAsGroup` does not remove; configMap/secret content is
  world-readable by default.
- OpenShift restricted SCCs constrain `runAsUser`, `fsGroup` and
  `supplementalGroups`, but not `runAsGroup` — an arbitrary primary gid is
  admitted.
- Istio itself uses the same trick (gid 1337 exclusion).

### Details

1. **Choose the gid.** Default to a constant (e.g. `7777`). At injection time,
   if any app container (or the pod) declares the same `runAsGroup`, bump to
   the first free value. Image-default gids are invisible to the injector;
   collisions with those are improbable (image defaults are 0 or = uid) and
   the value is overridable via the chart for the pathological case.
2. **Injector** (`pkg/agentconfig/container.go`): after resolving the
   inherited/configured SC, set `RunAsGroup` to the chosen gid on the *agent's
   copy* (deep-copied — must not mutate the app's SC). If the operator
   explicitly set `agent.securityContext.runAsGroup`, respect it.
3. **`AGENT_GID` env** (`pkg/agentconfig/initcontainer.go`): pass the chosen
   gid to the init container, alongside the existing `AGENT_UID`.
4. **`agentinit`**: replace `--uid-owner <agentUID>` with
   `--gid-owner <agentGID>` in all owner-based rules (the four TEL chain jumps
   and the mesh-bypass rules). Fallback when `AGENT_GID` is unset (config
   generated by an older traffic-manager): keep the current UID-based
   behavior, so a new agent image with an old manager degrades to today's
   semantics rather than breaking.
5. **Chart**: document that `agent.securityContext.runAsGroup` overrides the
   default.

### Rejected alternatives

- **Force a distinct UID**: breaks volume-permission inheritance and OpenShift
  SCC ranges — the very reasons the SC is inherited.
- **Destination-scoped bypass** (only exempt the traffic-manager's address):
  requires resolving the manager Service IP in the init container and goes
  stale if the Service is recreated; also changes behavior for agent dials to
  cluster IPs.
- **Supplemental-group marking**: supplemental groups are pod-scoped, so they
  cannot single out the agent container.

## Affected files (anticipated)

- `pkg/agentconfig/container.go` — assign the distinct `RunAsGroup`.
- `pkg/agentconfig/initcontainer.go` — `AGENT_GID` env (new `EnvAgentGID`
  constant in `sidecar.go`).
- `cmd/traffic/cmd/agentinit/agent_init.go` (+ test) — gid-based owner
  matches with uid fallback.
- `charts/telepresence-oss/` — docs for the override (no new value needed;
  `agent.securityContext` already exists).
- `CHANGELOG.yml`, docs regen.

## Testing

- **Unit**: agentinit rule shapes for gid-based matching and for the
  uid-fallback (no `AGENT_GID`); injector test that the agent SC gets the
  distinct gid, the app SC is not mutated, and an app-declared `runAsGroup`
  collision bumps the value.
- **Integration (gated Istio suite)**: extend with the #4156 observable — from
  the *app container* of an engaged, meshed workload, an HTTP request to a
  meshed service must carry the sidecar's marks (e.g. an Envoy-injected
  header), proving app traffic still traverses the mesh while the agent is
  injected. This fails today when uid collides, passes with the gid fix.
- Existing no-mesh suites stay green (gid match is a no-op without a mesh).

## Open questions

1. Default gid value: `7777`? (Istio reserves 1337; avoid that.)
2. Should the uid-based matches be kept *in addition* to gid (`--uid-owner X
   --gid-owner Y` ANDed) for defense in depth, or replaced outright? Replacing
   is simpler; ANDing protects against an app that shares the gid through an
   image default.

## Rollout

Phase 1: injector + `AGENT_GID` + agentinit gid matching with uid fallback,
unit tests.
Phase 2: Istio-suite extension + live verification on the minikube cluster.
Phase 3: changelog/docs, delete this plan.
